# 分层存储控制台（tier-control）

一个零依赖（Node ≥ 20，ESM）的分层存储实验系统：**热数据放在本地快盘**，**冷分区放在独立的慢速存储服务**（同一磁盘上的独立目录，读/写都注入可控延迟与带宽上限，并可注入网络中断、字节损坏）。查询命中冷层时可按需把分区回热到热盘；迁移、查询回热、空间回收可以同时发生，且始终保持三条硬不变量：

1. **迁移过程中绝不删除唯一副本**：先构建新的冷版本并逐对象校验，再登记目录并落盘，最后才排空读者租约、删除热副本。
2. **同一个冷分区不会被 N 个并发查询重复下载**：按 `数据集|范围|文件|分区|版本` 合并成一个共享取回任务，其余查询加入并等待同一个任务。
3. **查询始终读取固定版本**：查询开始即固定 `versionId` 与 `sha256`；期间发生的版本替换、回热校验失败、进程崩溃/恢复都不会让这次查询读到“另一版”或未校验的字节。

所有数据都是磁盘上的真实文件；网页上能看到每份数据当前的可读位置（`hot` / `cold` / `hot+cold` / 不可读）以及校验依据（SHA-256、manifest 校验和、租约/宽限原因、历史记录）。

## 快速开始

```bash
npm start            # 默认 http://127.0.0.1:4317 ，数据目录 ./data
PORT=8080 DATA_DIR=/tmp/tier npm start
npm test             # 27 个端到端/并发测试，串行执行
npm run reset        # 删除数据目录（默认 ./data，或 $DATA_DIR）
```

打开页面后：创建数据集 → 迁移到冷分区 → 清空热副本（或由容量回收触发）→ 查询（按文件 / 整分区回热）→ 观察共享任务、校验依据与一致性面板。顶部还可以调节冷读延迟/带宽、故障注入、取消策略、校验重试次数、旧版本宽限期。

数据目录结构：

```
<DATA_DIR>/
  catalog/catalog.json          # 唯一事实来源：可读位置、副本摘要、校验依据、历史、事件
  hot/<datasetId>/<fileId>-<sha12>.bin   # 内容寻址的热副本
  cold/partitions/<分区>/versions/<版本>/{manifest.json,objects/...}
  cold/tmp/                     # 迁移/版本替换的临时构建目录（启动时清理）
```

热文件用 `<fileId>-<sha12>` 内容寻址：替换内容写入新路径，绝不原地覆盖正在被读的旧 inode；同一份字节可被多个查询安全共享。

## 架构与关键实现

| 模块 | 职责 |
| --- | --- |
| `src/catalog.js` | 目录库。`readable` 只描述“现在真正能读到的层”；每个文件记录 hot/cold 副本的 `sha256`、`size`、`verifiedAt`、`evidence`；`history`/`events` 保留每次位置变更的依据。写盘为合并式单写者（dirty-flag），高并发下不会积压写链。 |
| `src/cold.js` | 独立慢速冷服务。`putVersion` 在 `tmp/` 构建，逐对象校验 SHA-256，最后写 manifest 并 `rename` 成正式版本（半成品永远不可见）；`retrieveFile` 注入基准延迟 + 分块带宽延迟，支持取消，支持 `error-once/always`、`corrupt-once/always` 故障注入。 |
| `src/storage.js` | 热盘。内容寻址、读者租约（`PathLeases`）、暂存区（staging）与“校验通过才转正”的 `promoteStaged`；删除文件前先排空租约。 |
| `src/migrations.js` | 迁移执行器：校验热源 → 构建临时冷版本 → 逐对象校验 → manifest 转正 → 提交目录并 `flush` → 排空租约后删热。任一步失败/取消都保留可读副本，并修正目录到磁盘实况。 |
| `src/retrievals.js` | 共享取回管理器。同键任务合并；每文件取回后复算 SHA-256，失败按 `maxVerifyRetries` 重试，坏字节永不登记；订阅者退订后按 `cancelPolicy` 决定任务是继续还是中止。 |
| `src/queries.js` | 查询引擎。固定版本与摘要；热读前在租约下复算摘要；热副本损坏/丢失/正在回收时回退冷层，取回后热读仍失败则“直接冷读”（`cold-direct`），全程仍校验 SHA-256。 |
| `src/versioning.js` / `src/versions.js` | 慢存储版本替换：构建并校验新冷版本 → 原子切换目录；旧版本保留，直到**没有查询固定它**且超过宽限期。版本 pin 由每次查询在开始时建立、结束时释放。 |
| `src/reclaim.js` | 空间回收：清理无目录引用的孤儿热文件（跳过有租约的）、按 LRU 在**热盘超出容量且冷副本摘要一致**时降级热副本、删除无 pin 且过宽限期的旧冷版本；dry-run 会列出每个动作及原因。 |
| `src/recovery.js` | 进程恢复：把中断的迁移/切换/回热/查询标记为 `interrupted`，重新复算热文件摘要，损坏或缺失则回退到冷副本；从不主动删除任何副本。 |
| `src/benchmark.js` | 同规格数据集对比“按文件读取”与“整分区回热”：并发 N 个查询，测首屏延迟、冷流量、热缓存增量、冷任务数/共享加入数。 |

HTTP 层（`src/server.js`）只做装配与参数校验；前端（`public/`）每 1.2 秒轮询 `/api/state`，展示数据集、每个文件的位置与校验依据、共享任务、版本/pin、事件、一致性问题。

### 迁移的固定顺序（并发安全的根据）

```
校验热源 → 冷层构建 tmp 版本（逐对象写入+校验）→ manifest 转正（rename）
        → 目录提交冷副本 + fsync/flush → 排空读者租约 → 删除热副本
        → 旧冷版本进入宽限期；有查询 pin 时回收跳过
```

- 在“目录提交冷副本”之前崩溃：磁盘上只有不可见/未登记的冷版本，热副本仍在，恢复后照常读热。
- 在“提交之后、删热之前”崩溃：两份副本都在，恢复后读任何一份都校验一致。
- 取消迁移：已经删掉的热副本对应文件一定有已校验冷副本；未删的保留，可读位置按磁盘实况修正。
- 删除热文件前必须获得租约并排空，正在读的查询不会看到 `ENOENT`。

### 查询读写路径

```
查询(dataset, file, versionId?, mode) 
  ├─ 热副本摘要匹配 → 租约内复算 SHA-256 → 返回（x-tier-read-from: hot）
  ├─ 否则固定版本/摘要 → 加入或创建共享取回任务
  │     ├─ 按文件（mode=file）：只下载该文件
  │     └─ 整分区（mode=reheat-partition）：下载该版本全部分区对象
  ├─ 取回后热读；若热副本又被回收 → 直接冷读并校验（cold-direct）
  └─ 任何校验失败都不会返回字节；502 中写明“可读位置保持为 …”
```

响应头包含 `x-tier-read-from`、`x-tier-sha256`、`x-tier-verified`、`x-tier-version`、`x-tier-query-id`、`x-tier-shared-task`、`x-tier-shared-join`、`x-tier-cancel-policy`，可作为每次读取的校验依据。

### 取消查询后共享任务是否继续

由设置 `cancelPolicy` 决定，且每次查询都会记录 `taskContinuedAfterCancel`：

- `continue`（默认）：最后一个订阅者取消后，任务**继续**下载、校验并缓存到热层，后续查询直接命中，形成“取消一个人、服务后来者”的效果。
- `cancel-if-idle`：无人订阅时立即 `abort()` 网络传输；已经写下的暂存字节被清理，可读位置不变。

两种策略下，发起查询的客户端都立即收到 499/取消语义，不会阻塞共享任务；网页的共享任务面板会显示“查询取消后仍在继续”。

### 版本替换与固定版本读

- 替换：生成新内容 → 构建新冷版本并逐对象校验 → 原子转为正式版本 → 目录原子切换；旧版本目录保留。
- 每次查询在开始时 pin 住 `(分区, 版本)`；回收只删除 **pin 数 = 0 且超过 `versionGraceMs`** 的旧版本，所以固定版本查询在替换后仍能读到旧内容。
- 回热校验失败：重试配置次数后仍失败则登记 `lastError`、保持原可读位置（通常是 cold），不会把坏字节登记成热副本；若热副本此前已被删掉，查询回退为直接冷读同一固定版本。
- 进程恢复：中断时正在运行的回热/查询被标记 `interrupted`，未完成的迁移标记 `interrupted`；热文件按 SHA-256 复验，坏/缺失则把 `readable` 修正为 `cold`，不删除任何副本。

## 网页上能看到什么

- **概览卡片**：冷读取次数/流量、共享加入次数、回收字节、中断/校验失败计数。
- **存储分层**：热盘用量与容量、冷层用量，四步切换顺序示意，以及延迟/带宽/故障/取消策略/重试/宽限期控件。
- **数据集**：每个文件的 `readable` 徽标（hot / cold / hot+cold）、hot/cold 各自的 SHA-256 与校验依据、`lastError`、历史；可对单文件查询或按文件/整分区回热。
- **共享取回任务**：作用域、订阅人数、已下载/总字节、复用文件数、当前文件、是否处于“无人订阅但继续”。
- **读取策略对比**：一键跑两组同规格数据集并给出表格与原始数据。
- **冷分区与版本**：每个冷版本的 manifest 校验和、文件数、字节数、是否被 pin、是否为孤儿，可对某个版本发起回收。
- **一致性**：`NO_REPLICA`、`READABLE_*_MISSING`、`REPLICA_MISMATCH`、`MIGRATION_STALLED` 等检查结果（正常情况下为空）。
- **事件与校验依据** / **操作输出**：最近的迁移、回热、回退、回收、恢复事件及其证据。

## 对比实验：按文件读取 vs 整分区回热

一次典型运行（6 个文件 × 256 KiB，4 个并发查询同一文件，冷读延迟 35 ms、带宽 6 MiB/s）：

| 策略 | 首屏延迟（最快查询） | 最慢查询 | 冷流量 | 热缓存增量 | 冷任务 | 共享加入 |
| --- | --- | --- | --- | --- | --- | --- |
| 按文件读取 | ≈ 0.24 s | ≈ 0.24 s | ≈ 256 KiB | +256 KiB | 1 | 3 |
| 整分区回热 | ≈ 0.77 s | ≈ 0.77 s | ≈ 1.5 MiB | +1.5 MiB | 1 | 3 |

结论（数值随机器波动，可在页面重跑）：

- **首屏延迟**：按文件读取明显更快。它只取当前文件；整分区回热要等整个版本下完（冷带宽是瓶颈），延迟随分区大小线性增长。
- **冷流量**：按文件读取只花一个文件的字节；整分区回热花整个分区的字节，差距约等于分区文件数。
- **缓存占用**：两者都只产生 **1 个冷任务**（N 个并发查询共享同一次下载），但按文件只占被查询文件的缓存，整分区占整个分区。
- **选择建议**：单文件/少量文件命中且分区很大时用按文件读取；预计后续会连续访问分区内大部分文件、或希望“一次延迟换长期热命中”时用整分区回热。两者的共享任务语义相同，N 个并发查询都只下载一次。

`POST /api/benchmark {files, sizeMb, clients}` 返回每个策略的 `firstByteMs`、`slowestQueryMs`、`coldBytes`、`hotCacheDeltaBytes`、`coldTasks`、`sharedJoins`。

## 主要 HTTP API

| 方法 & 路径 | 说明 |
| --- | --- |
| `GET /api/state` | 目录库快照 + 运行时任务/租约/pin + 容量用量 + 一致性检查 |
| `GET /api/events?limit=` / `GET /api/datasets` / `GET /api/datasets/:id` | 事件、数据集 |
| `POST /api/datasets` | `{name, count, sizeMb, seed?}` 创建数据集并写入校验后的热文件 |
| `POST /api/datasets/:id/migrate` / `.../migrate/cancel` / `.../migrate/wait` | 启动/取消/等待迁移 |
| `POST /api/datasets/:id/query` | `{fileId, mode: auto\|file\|reheat-partition, versionId?, cancelAfterMs?}`，返回字节流与 `x-tier-*` 头 |
| `POST /api/datasets/:id/reheat` | `{scope: file\|dataset, fileId?}` 创建/加入共享取回任务 |
| `POST /api/datasets/:id/evict-hot` | 所有文件都有校验过的冷副本时释放热副本 |
| `POST /api/tasks/:id/cancel` / `GET /api/tasks` | 取消/查看共享取回任务与 pin |
| `POST /api/datasets/:id/version`（+ `/version/cancel`） | 慢存储版本替换 |
| `GET /api/partitions` / `POST /api/partitions` | 冷分区与版本（含 pin、字节数） |
| `POST /api/benchmark` / `POST /api/reclaim`（`dryRun`）/ `POST /api/recovery`（`verifyCold`） | 对比、回收、恢复 |
| `POST /api/settings` | 修改延迟/带宽/故障/取消策略/宽限期/重试次数/热盘容量 |

冷故障注入可指定文件（`coldFaultFileId`），便于在网页上精确演示“回热校验失败时保留原可读位置”。

## 测试覆盖（`npm test`，27 项）

- 迁移：冷副本校验通过后才登记并删热；取消迁移不删唯一副本；`SIGKILL` 式中断后重启标记 `interrupted` 且仍读热。
- 查询：按文件只下载一个文件；4/10 个并发查询只产生一个共享任务；取消后按策略继续/中止；网络故障时 502 且可读位置保持冷层；损坏一次重试成功并留证据；持续损坏不产生热副本。
- 版本：替换后新内容生效；替换期间固定旧版本查询继续读旧内容，回收因 pin 跳过；替换后按 `versionId` 仍可读旧内容；替换失败保留旧版本。
- 回收/恢复：孤儿热文件清理、有租约跳过、宽限期内旧版本跳过；热文件被外部删除后回退冷层；冷副本损坏但热副本完好时继续读热；进程恢复标记中断任务；篡改热副本后查询回退冷层并带回证据。
- 并发：迁移 + 查询 + 回收循环无失败且一致性为空；回热与迁移/回收并发；十个并发按文件查询只下载一次。
- HTTP：完整流程、结构化错误（400/404/403 路径穿越）、版本替换与取消字段。

## 已知边界

- 冷服务是同一机器上的独立目录 + 注入延迟（便于复现与观察），**不是**真实分布式存储；`catalog.json` 为单进程内存状态 + 原子写盘的合并式持久化，不支持多进程同时写。
- 示例数据规模为 KB–MB 级，查询把完整内容读入内存后返回（便于对比“首屏”与校验）；真实系统应改为流式，并在流式读取时保持租约。
- 所有 SHA-256 校验都是读取/写入后的实际复算；网页展示的即为这些复算结果与目录记录，不做任何“假定正确”。
